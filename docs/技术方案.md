## 1. 作品概述

SRC-VulnMiner 是一个面向安全攻防场景的可落地漏洞挖掘Agent，针对Web应用安全测试，实现从任务输入到报告输出的**端到端全流程自动化**。Agent 能够自主完成任务拆解、信息采集、分析研判、验证测试、结果汇总，可直接对接线上靶场完成闯关任务。

核心定位：**LLM 是驾驶员，工具是双手，规则是参考，验证是裁决**。区别于"大模型问答"式伪Agent，本作品通过函数调用（Function Calling）实现真正的工具编排与自主决策，并通过会话持久化、约束管理和证据链记录保证工程可落地性。

### 2.1 阶段化工作流（LLM自主流转）

Agent 工作在五个阶段：任务解析 → 信息采集 → 分析推理 → 验证执行 → 结果汇总。与固定流水线不同，阶段切换由 LLM 根据实际进展自主决策，支持回退（验证失败返回分析阶段）和跳跃（信息充分时直接进入验证）。

### 2.2 双引擎分析设计

- **规则引擎（快速通道）**：基于 YAML 规则的确定性模式匹配，检测危险函数调用（Sink）、用户输入来源（Source）、SQL拼接模式等。20+条规则覆盖 SQL注入/XSS/SSRF/IDOR/路径遍历/命令注入。零幻觉、零成本，结果作为 LLM 的辅助输入。
- **LLM引擎（深度通道）**：理解代码语义，识别规则引擎无法覆盖的业务逻辑漏洞（如 IDOR 越权、验证绕过），并通过多轮反思降低误报。

### 2.3 任务边界控制

约束管理器在三个层面设防：
1. **范围约束**：目标主机白名单校验，越界请求直接拒绝
2. **操作约束**：破坏性操作黑名单（DROP/DELETE/rm等），Python执行和PoC构造时拦截
3. **能力边界**：LLM 识别超出自身能力的场景（如二进制漏洞），标记需人工介入而非强行输出结论

## 3. 核心方法

### 3.1 LLM驱动的工具编排循环

每轮循环：LLM 产生思考（reasoning）→ 调用一个或多个工具 → 工具结果反馈 → LLM 基于新信息决策。会话消息完整保留，支持 30+ 轮次的长程任务。关键设计：

- **推理模型适配**：reasoning 模型的 reasoning_content 与 content 分离处理，截断时优雅降级
- **结果截断策略**：工具返回结果限制 3000 字符，避免上下文膨胀
- **会话自动保存**：每轮结束持久化 JSON，支持中断恢复

### 3.2 漏洞验证与证据链

验证遵循"先怀疑后确认"原则：
- 每个发现默认 L1 证据级（分析推断），只有实际发送 payload 并观察到预期响应才升级 L2（实测验证）
- 验证 payload 严格非破坏性：SQL注入仅布尔/报错测试、XSS 仅无害 alert、SSRF 仅内网探测
- **高危类型（路径遍历、命令注入）主动跳过实测**——这是工程可落地性的体现：识别"验证动作本身会破坏测试目标"的场景

### 3.3 防幻觉与降误报

- 规则引擎结果独立于 LLM 存在，LLM 无法凭空"创造"代码证据
- 会话层去重：同类型同位置发现自动合并
- 证据分级：L1（分析）与 L2（验证）严格区分，报告明确标注
- 已知误报模式（测试文件、参数化查询、硬编码值）由规则引擎识别

### 3.4 HTTP 请求纪律（防卡死设计）

上一版本（固定流水线）演示时曾因请求重试循环导致系统卡死。v2 彻底重构：
- 验证请求**零重试**，10 秒硬超时
- 靶场 `threaded=True` 部署，单请求挂起不影响其他探测
- 连续超时检测：目标失联立即停止探测转入报告

## 4. 实验结果

### 4.1 演示靶场测试

靶场：自建 Flask 应用，6 种已知漏洞（SQL注入/反射XSS/IDOR/SSRF/路径遍历/命令注入），全部数据虚构脱敏。

| 指标 | 数值 |
|------|------|
| 漏洞发现率 | 6/6（100%）|
| 实测验证数 | 4（SQLi/XSS/IDOR/SSRF）|
| 误报数 | 0 |
| 总耗时 | 65.2 秒 |
| LLM 调用 | 17 次，$0.18 |
| 人工介入 | 0 次（0%）|
| 单漏洞发现平均时长 | 约 11 秒 |

### 4.2 关键验证结果摘录

- **SQL注入**：`POST /login username="' OR '1'='1 --"` 成功绕过登录，返回 "Login successful! Welcome, alice_demo"
- **XSS**：`GET /search?q=<script>alert(1)</script>` 脚本标签未编码反射
- **IDOR**：`GET /user/2` 无认证访问他人资料（role=admin）
- **SSRF**：`GET /fetch?url=http://127.0.0.1:5000/user/1` 服务器执行内部请求并返回结果

### 4.3 架构迭代对比（v1 vs v2）

| 维度 | v1 固定流水线 | v2 LLM驱动 |
|------|--------------|------------|
| 漏洞发现 | 0 confirmed（全 uncertain）| 6/6 确认 |
| 实测验证 | 0 | 4 |
| 演示完成度 | 卡死/超时循环 | 65秒完成 |
| 误报噪音 | 大量 Server 头等低价值告警 | 0 误报 |
| 决策依据 | 规则置信度阈值 | LLM 语义理解+实测证据 |

结论：安全漏洞挖掘需要**语义级理解**（这个参数流向哪里、这条数据有没有鉴权），纯规则阈值无法胜任；而纯 LLM 无工具约束则无法验证。LLM 驱动 + 工具编排 + 证据链是最优组合。

## 5. 创新点

1. **多轮自主反思**：LLM 每轮基于工具反馈迭代认知，支持"探测→怀疑→验证→确认/放弃"完整认知循环，而非单次问答
2. **工具调用编排**：7 工具 Function Calling 设计，LLM 自主编排调用序列；HTTP 零重试+硬超时的工程纪律保证系统不死锁
3. **漏洞自动验证与证据分级**：L1/L2 证据体系，验证过程自动产生可核验的请求-响应证据，报告全部可复现
4. **安全边界主动控制**：识别"验证即破坏"的场景主动放弃实测、约束管理器多层拦截、Python 执行全审计
5. **推理模型工程适配**：针对 reasoning 模型的 content/reasoning_content 分离处理与 token 预算优化

## 6. 工程完整性

- **源码**：Python 3.10+，13 个自动化测试（规则引擎 7 + 集成 6）全部通过
- **部署**：`pip install -r requirements.txt` 一键安装；config.yaml 配置 LLM 与行为参数
- **复现**：`python demos/demo_run.py --auto` 一键启动靶场并运行 Agent，评测环境可完整复现本文实验数据
- **接口**：标准 JSON 输入输出，退出码约定（0=已验证/2=未验证/3=错误），适配靶场调用
- **可观测**：全流程日志、每轮 LLM 决策记录、Python 执行审计日志、会话 JSON 存档

## 7. 不足与改进方向

- 当前仅覆盖 Web 应用漏洞，二进制方向未涉及
- 路径遍历/命令注入验证策略保守（跳过实测），后续可通过更隔离的靶场环境补齐
- LLM 轮次效率可优化（当前存在重复 session_status 查询），可引入轮次预算自适应
