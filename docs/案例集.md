# 脱敏漏洞实践案例集

> 以下案例全部来自自建演示靶场，**所有数据均为虚构**：IP 已脱敏（127.x.x.x）、账号为演示虚构账号（alice_demo 等）、不涉及任何真实系统与真实数据。
> 每个案例完整展示：**线索 → 分析过程 → 验证逻辑 → 证据**，可直接复现。

## 案例 1：SQL 注入（登录绕过）— 已验证 L2

**漏洞线索**
- 规则引擎扫描源码，命中危险函数 `execute` 与 f-string SQL 拼接模式（`app.py:132`）：
  ```python
  query = f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'"
  cursor = DB.execute(query)   # ← 用户输入直接拼接进SQL
  ```

**分析过程**
- 数据流追踪：`request.form.get("username")` → `username` 变量 → f-string 拼接 → `execute(query)`，全程无参数化处理
- 端点定位：`@app.route("/login", methods=["GET", "POST"])` → `POST /login`

**验证逻辑**（非破坏性，仅 SELECT）
1. 发送 payload：`username="' OR '1'='1 --"`, `password=x`
2. 预期：SQL 布尔恒真，绕过密码校验

**验证证据**
```
POST /login  body: username="' OR '1'='1 --"&password=x
响应: "Login successful! Welcome, alice_demo (Role: user)"
→ 密码错误但登录成功，SQL 注入确认
```

## 案例 2：反射型 XSS — 已验证 L2

**漏洞线索**
- 源码 `app.py:168-175`：搜索参数直接拼接 HTML，无编码：
  ```python
  query = request.args.get("q", "")
  content = f"<h3>Search Results for: {query}</h3>"
  ```

**分析过程**
- 用户输入流向：`request.args.get("q")` → HTML body 两处反射（input value 属性 + 结果标题）
- 无 `escape()` / `htmlspecialchars` / CSP 防护

**验证逻辑**
1. 发送 `GET /search?q=<script>alert(1)</script>`
2. 检查响应中 script 标签是否原样出现（未转义）

**验证证据**
```
GET /search?q=<script>alert(1)</script>
响应: ...value="<script>alert(1)</script>...<h3>Search Results for: <script>alert(1)</script></h3>...
→ script 标签在可执行上下文原样反射，XSS 确认
```

## 案例 3：IDOR 越权访问 — 已验证 L2

**漏洞线索**
- 源码 `app.py:189-204`：用户资料端点无任何鉴权与属主校验：
  ```python
  @app.route("/user/<int:user_id>")
  def user_profile(user_id: int):
      cursor = DB.execute("SELECT * FROM users WHERE id = ?", (user_id,))
      # ← 没有检查当前登录用户是否为本人
  ```

**分析过程**
- 规则引擎标记该端点为资源 ID 直取模式
- LLM 语义分析：无 session 校验、无 ownership 检查、相邻 ID 可遍历

**验证逻辑**（只读，不修改任何数据）
1. 不携带任何认证信息，直接请求 `GET /user/2`
2. 预期：返回其他用户的完整资料

**验证证据**
```
GET /user/2（无Cookie、无Token）
响应: "Username: bob_demo, Email: bob@demo.local, Role: admin"
→ 未认证访问他人资料成功，IDOR 确认
```

## 案例 4：SSRF 服务端请求伪造 — 已验证 L2

**漏洞线索**
- 源码 `app.py:222-223`：URL 参数直传服务端请求库：
  ```python
  url = request.args.get("url", "")
  response = urllib.request.urlopen(url, timeout=5)   # ← 用户控制的URL
  ```

**分析过程**
- 规则引擎命中 `urlopen` 危险函数 + `request.args` 来源
- 无协议/主机白名单校验

**验证逻辑**（仅访问本靶场自身，不涉及外部）
1. 发送 `GET /fetch?url=http://127.0.0.1:5000/user/1`
2. 预期：服务器发起内部请求并把响应返回给客户端

**验证证据**
```
GET /fetch?url=http://127.0.0.1:5000/user/1
响应: 服务器返回了 /user/1 页面的完整内容
→ 服务端执行了内部请求，SSRF 确认
```

## 案例 5：路径遍历 — L1（分析确认，实测跳过）

**漏洞线索**
- 源码 `app.py:272-275`：文件名参数直接拼接到文件路径：
  ```python
  filename = request.args.get("file", "")
  file_path = os.path.join(demo_dir, filename)   # ← 无路径规范化
  ```

**分析过程**
- `os.path.join` 对 `../../` 不设防，规则引擎命中 `open` 危险函数 + 用户输入
- 预期可读任意文件

**验证策略说明**
- 该漏洞的实测验证会在测试目标上触发文件系统异常路径访问，导致靶场进程挂起（已验证此风险）。Agent **主动识别"验证即破坏"场景，标记 L1 待人工复核**——这正是任务边界控制的设计体现。

## 案例 6：命令注入 — L1（分析确认，实测跳过）

**漏洞线索**
- 源码 `app.py:315-318`：用户输入直接进入 shell：
  ```python
  host = request.args.get("host", "")
  cmd = f"ping -c 1 {host}"
  output = subprocess.check_output(cmd, shell=True)   # ← shell=True + 用户输入
  ```

**分析过程**
- 规则引擎命中 `subprocess` + `shell=True` 高置信模式（0.85）
- 无输入过滤：`; ls` 等元字符可注入

**验证策略说明**
- 同案例 5：实测会执行目标系统命令，非破坏性验证手段有限，标记 L1 待人工复核。
